# AuditCore Preview Guide

هذا الملف يشرح كيفية تشغيل وضع المعاينة (Preview) لمشروع AuditCore، وما الذي يعمل مباشرة، وما الذي يحتاج إلى seed أو تشغيل الخلفية محليًا.

## ملخص سريع

في وضع المعاينة:
- يمكن للواجهة الأمامية العمل والظهور بشكل طبيعي.
- تسجيل الدخول يعتمد على Supabase Auth.
- جلب ملف المستخدم كان يعتمد سابقًا على `FastAPI` عبر `api.me()` على:
  - `http://localhost:8000`
- تم الآن إضافة **fallback** بحيث إذا كانت الخلفية غير متاحة في الـ preview، يتم جلب ملف المستخدم مباشرة من Supabase من جدول `public.users`.

## الحسابات التجريبية

الحسابات التالية لا تظهر ولا تعمل إلا إذا تم تنفيذ seed على مشروع Supabase المستهدف:

## ملاحظتان مهمتان في الـ Preview

### 1) المستخدمون لا يوجدون إلا بعد تنفيذ seed

إذا لم يتم تنفيذ seed على مشروع Supabase، فلن تكون هذه الحسابات موجودة في Supabase Auth، وبالتالي سيفشل تسجيل الدخول برسالة:

- `البريد الإلكتروني أو كلمة المرور غير صحيحة`

نفّذ أحد الخيارين التاليين على المشروع المستهدف:

```bash
./setup.sh
```

أو:

```bash
python backend/scripts/seed.py
```

مع التأكد من ضبط المتغيرات التالية في البيئة:

- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

ويجب أن يكون التنفيذ ضد مشروع Supabase الصحيح.

## 2) تسجيل الدخول في المعاينة قد يفشل عند خطوة profile إذا كانت الخلفية متوقفة

قبل التعديل، كان `useAuth.login` يعتمد على:

- `api.me()`
- والذي يستدعي `FastAPI` على `http://localhost:8000`

في وضع المعاينة، غالبًا لا تكون الخلفية شغالة، لذلك:
- Supabase Auth قد ينجح
- لكن جلب الملف الشخصي من `FastAPI` قد يفشل

### ما الذي تم إصلاحه؟

تمت إضافة fallback جديد:
- إذا تعذّر الوصول إلى `FastAPI`
- يتم جلب بيانات المستخدم مباشرة من Supabase من جدول `public.users`

وبذلك تصبح المعاينة قابلة للاستخدام حتى دون تشغيل Docker backend، بشرط:
- وجود المستخدم في Supabase Auth
- ووجود ملفه في `public.users`

## سلوك صفحة تسجيل الدخول الآن

صفحة تسجيل الدخول تقوم بالآتي:

1. التحقق من إمكانية الوصول إلى `FastAPI`
2. التحقق من وجود المستخدمين التجريبيين في Supabase
3. عرض تنبيه إذا كانت الخلفية غير متاحة
4. عرض إرشادات لتشغيل seed إذا لم يتم العثور على المستخدمين
5. عرض الحسابات التجريبية الجاهزة بشكل واضح إذا كانت موجودة

## تشغيل الخلفية محليًا للمعاينة

إذا أردت أن تعمل `api.me()` بشكلها الطبيعي دون fallback، شغّل الخلفية محليًا.

أضفنا سكربتًا سريعًا لهذا الغرض:

```bash
./preview-backend.sh
```

يقوم هذا السكربت بـ:
- تشغيل `redis` و `backend`
- انتظار جاهزية `FastAPI`
- تشغيل migrations
- تطبيق RLS
- تنفيذ seed للمستخدمين التجريبيين

بعد نجاحه، ستكون الخلفية متاحة على:

- `http://localhost:8000/docs`

## الإعداد الكامل

للتشغيل الكامل للمشروع:

```bash
./setup.sh
```

يقوم هذا السكربت بإعداد البيئة وتشغيل الحاويات وتطبيق migrations وseed.

## سيناريوهات شائعة

### الحالة 1: الواجهة تعمل لكن كل الحسابات ترفض تسجيل الدخول

السبب المحتمل:
- لم يتم تنفيذ seed بعد

الحل:
```bash
./setup.sh
```
أو:
```bash
python backend/scripts/seed.py
```

### الحالة 2: تسجيل الدخول ينجح في Supabase لكن التطبيق لا ينتقل للوحة التحكم

السبب المحتمل سابقًا:
- `api.me()` يفشل لأن `FastAPI` غير شغال

الوضع الحالي:
- يوجد fallback تلقائي إلى Supabase

إذا استمرت المشكلة:
- تحقق من وجود صف المستخدم داخل `public.users`
- وتحقق من أن `auth_user_id` أو البريد الإلكتروني مربوط بشكل صحيح

### الحالة 3: تريد محاكاة البيئة الكاملة محليًا

شغّل:
```bash
./preview-backend.sh
```
أو:
```bash
./setup.sh
```

## التشخيص ومعالجة الأخطاء (Error handling)

لتسهيل معرفة الخطوة الفاشلة فعليًا أثناء تسجيل الدخول:

- كل طلب للخلفية يرمي الآن `ApiError` يحمل: `status` (رمز HTTP، و`0` يعني انقطاع
  الشبكة/الخلفية غير متاحة)، و`path` (المسار)، و`detail` (الرسالة من الخادم).
- تسجيل الدخول يسجّل كل خطوة في الـ console بادئة `[auth]`:
  1. `POST /auth/login` (وكيل تحديد المعدّل) ← أو fallback إلى Supabase مباشرة،
  2. `GET /auth/me` ← أو fallback إلى ملف Supabase.
- عند فشل تسجيل الدخول يظهر **toast** يوضّح المسار ورمز الحالة والتفصيل، إضافةً
  إلى `console.error` كامل — بدلاً من رسالة عامة فقط.
- فشل `api.me()` يُعدّ حالة **قابلة للتعافي**: تستمر الملاحة ويُقرأ الملف من
  Supabase، ولا ينهار مسار `/login` أبدًا.

## فحص صحة الخلفية وتبديل الوضع

- نقطة النهاية `GET /health` في الخلفية تُرجع فحصًا عميقًا
  (`database` / `redis` / `rls`) وحالة عامة (`ok` / `degraded`).
- الواجهة تستخدم `src/lib/backendHealth.ts::checkBackendHealth()` (مع مهلة قصيرة)
  لتقرير الوضع: `full` عند توفّر الخلفية، أو `supabase-only` عند تعذّرها — فيظهر
  تنبيه وضع المعاينة ويُفعَّل الـ fallback تلقائيًا.
